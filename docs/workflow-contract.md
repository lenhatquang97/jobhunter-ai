# Candidate workflow interface v2

This additive interface extends chat-contract.md. Odoo20 owns workflow records. Existing chat clients, read callbacks and sources remain compatible. No unrestricted model methods/domains. Names below are fixed across implementations.

## Requests and identity

Submit gains optional `workflow = {action: 'screen'|'schedule'|'report'|'confirm', applicant_id: positive int, data: object = {}}`. Browser sends it through `messages.send`. No browser UID/company/case ownership authority. Selected/focused applicant must be one of the conversation's explicitly selected application IDs; an action lacking an unambiguous applicant returns Needs input. `data` is limited to the specific action. All reads remain original-user, company-scoped. Backend persists conversation/application associations and per-run workflow in a new related table, avoiding destructive ALTER/reset of existing data. Historical conversations remain unassociated until explicit candidate selection.

Natural-language requests can invoke the strict Orchestrator function `candidate_workflow` with `{action:'screen'|'schedule'|'report',applicant_id:int|null}`. It is local routing, not an Odoo tool. Resolve only explicit selected applicant/focus; never guess from prior unrelated chat. Pass current user text and saved workflow context to specialists, not other candidate chat transcripts.

## Native BFF operations

- `workflow.get {applicant_id}` returns `{case:Case}` after normal user access check; may create only that user's case. This operation is explicitly a mutation and CSRF validated, like all existing BFF requests.
- `workflow.criteria.approve {case_id,version}` explicitly approves exactly the current job/source-derived criteria snapshot. It cannot be invoked by a model callback.
- `messages.send` with workflow.action=confirm requires `data={draft_version:positive int}`. Before issuing the run grant, Odoo records an approval tied to the client_message_id, case, exact draft version/hash, owner and run. Grant callback scope includes the exact applicant and approval. Other workflow requests cannot receive confirm permission. The browser button label is Confirm booking & send.
- `workflow.revoke {case_id,session_id}` revokes only the user's candidate session; this does not silently cancel a committed calendar event.

## Signed tool callback operations

All use existing `/jobhunter/chat/tool`, wrapper `{arguments:...,context_refs:[...]}` and grant validation. Add these operation names only to appropriate scoped grants. Callback replies preserve `{ok,data,sources,error?}`.

1. `workflow_context {applicant_id}` -> `data={case:Case}`; sources include verified job/applicant + current saved artifact/answer references. Case includes document metadata IDs; document binaries continue through existing read_document. Reusable stale artifacts are omitted/marked outdated; revoked dependencies are hidden.
2. `workflow_save {case_id,expected_version,kind:'screening'|'report'|'interview_summary',content:object,sources:SourceRef[]}` -> data.case. Enforce owner, approved/current criteria, source access/version, bounded payloads, correct candidate and immutable artifact version. Saved artifacts gain their own verifiable SourceRef.
3. `workflow_schedule {case_id,expected_version,schedule:ScheduleInput}` -> data.case. Merge supplied non-null fields with this case's unconfirmed draft, validate deterministically, return missing inputs/issues/slots and exact draft_version. No calendar or mail writes. Change invalidates prior guide/approval.
4. `workflow_prepare {case_id,expected_version,language:'en'|'vi',questions:Question[5]}` -> data.case. Requires complete current scheduling draft. Persist guide bound to criteria/draft version; no session link, calendar or mail yet.
5. `workflow_confirm {case_id,draft_version}` -> data.case. Requires this run's explicit approval capability. Lock case, verify exact unchanged draft/criteria/source/approval, recheck permitted Odoo calendar conflicts, atomically create one event/session and queue one candidate mail (core calendar mail suppressed). Retry of same approval returns existing references. No legacy methods. Only named, readable internal users' calendars are checked; external availability is supplied, not claimed verified. Candidate links/credentials never enter model tools/events; return session ID and mail status, not bearer token.

`Case` public fields: `id,applicant_id,job_id,version,applicant_name,candidate_email,criteria_version,criteria_approved,criteria:[{id,text}],documents:[{id,name}],screening:Artifact|null,schedule:Draft|null,interview:SessionSummary|null,report:Artifact|null,interview_summary:Artifact|null`. Optional artifact/session entries explicitly state outdated/unavailable. Applicant email is field-access checked; fixture uses netlink269@gmail.com. Case versions increment on logical changes, and all write operations reject stale expected versions. UI always refreshes case after terminal workflow run.

`Artifact`: `{id,kind,content,sources,source_state,version}`. Findings content: `{summary,findings:[{criterion_id,status:'supported'|'partial'|'unknown'|'conflicting',finding,citations:[{source_key,quote}],question}]}`. Require all criteria once; factual findings cite nonempty exact quotations and source keys. Unknown without evidence may have no citations. Report/interview-summary content: `{text}` with normal verified [S#] citations. Artifact payloads may not contain score/rank/verdict fields.

`ScheduleInput` fields all optional/nullable for missing input: `start` (ISO local datetime, no implicit timezone), `duration_minutes` (15..180), `participant_count` (1..10, includes candidate, excludes AI), `participants` (up to10 objects `{name,email,timezone,availability:[{start,end}],user_id:int|null}`), `timezone` (IANA, applies to requested start), `candidate_email`. Every named participant needs explicit IANA zone and supplied availability, except internal calendar access may verify their availability for requested slot. Dates in availability are local to that participant. No guessed zones. Reject nonexistent/ambiguous DST times; request an unambiguous replacement. Requested slot must fit all supplied windows and readable internal calendars. Missing fields => Draft.status=needs_input; full valid draft => ready. `Draft` includes `version,status,missing,issues,schedule,starts_at_utc,ends_at_utc,display_times,email_preview,guide_ready,booking:{event_id,session_id,mail_status}|null`. Recipient must match explicitly selected candidate/supplied override shown in preview; never silently write applicant email.

`Question`: `{criterion_id,question,follow_up:string|null}`; exactly5 main questions, at most1 neutral follow-up each. `SessionSummary`: `{id,status:'prepared'|'awaiting_answers'|'in_progress'|'completed'|'partial'|'revoked'|'expired',submitted_count,question_count,answers:[{id,question,answer}],mail_status}`. All source-bearing fields are bounded and access checked.

## Candidate page and source validation

Odoo provides `/jobhunter/interview/<opaque-token>` and session-scoped JSONRPC actions get/answer/finish. Store token hashes only, expire within7days; logs redact tokens, page has no external assets/referrers. Recheck owner/candidate/company access and original job/source version each request. Validate CSRF on mutations, token status and exact current question. Answer submission `{question_id,client_answer_id,text}` is idempotent; immutable saved answers, max10000chars, no arbitrary record IDs. Resume current unanswered question; finish explicitly preserves partial state. Possessing a link establishes session access, not independent identity verification. No recruitment browsing or read tools are available to this route.

SourceRef.model additionally permits `jobhunter.chat.case`, `jobhunter.chat.artifact`, `jobhunter.chat.answer`. Source checksum/write_date and parent case permissions must be checked by validate_sources before delivery/history/reuse. An artifact carries original source dependencies; changes/revocation cascade state. Source links use Odoo forms under normal user permissions; answers remain private to owning recruiter and scoped candidate session.

## Pluggable specialist adapters (latest user clarification)

Filter, Schedule, Interview and Report are adapter slots, not new specialist implementations. The user will plug their friends' code in later. No current RAG scoring/ranking action is automatically invoked. Normal runtime defaults all four slots to unavailable and never silently falls back to replacement prompts. Deterministic test adapters are isolated to test configuration; successful E2E proves hosting/orchestration, not the absent friends' implementation.

Server configuration `JOBHUNTER_AGENT_ADAPTERS` is a JSON object mapping role names to trusted installed `module:factory` entrypoints. Each zero-argument factory returns an object implementing `async invoke(assignment:dict,runtime)->dict`, optionally `async close()`. Assignment contains contract_version2.0, role, request, current case, verified registry, mode, handoff_name and output_schema; never capabilities or provider credentials. Return the strict handoff directly, or `{text: cited prose}` for Report/interview summary. The runtime provides `stream(messages,tools,instructions)` for bounded shared model access; adapter code supplies its own specialist instructions. Adapter-owned model calls must use this gateway, disable private retries and respect the enclosing cancellation/deadline. Adapters receive retrieved evidence, not business-write tools. Only the host invokes validated scoped Odoo writes after checking handoffs/approval.

## Execution and events

Workflow runs invoke actual configured adapters and existing typed agent/tool events. Orchestrator routes, Filter returns strict findings, Schedule returns strict ScheduleInput, Interview returns strict five-question guide or submitted-answer summary, Report returns cited final prose. No fake specialist event on a role that did not execute. Preserve120s/6provider/8business tool limits. Empty/unfinished interviews yield an incomplete Report, never invented answers. Source text is always untrusted. Confirmation is deterministic execution of previously reviewed Schedule/Interview handoff; record actual tool step without pretending a new model call.

Live email disabled without configured publicHTTPS and SMTP. Disposable E2E explicitly enables local captured mail/localhost links in its own test configuration only. SMTP accepted is not inbox delivered; unknown delivery cannot be automatically resent. Core mail can retry only definitively unsent queue items; ambiguous acceptance is recorded unknown.


## Recruitment panel and migrated specialists (approved extension, 2026-10-31)

Runtime addon ownership is now `jobhunter-ai/odoo/addons/t10_jobhunter_chat`; copied original RAG addons are import references, never installed by this stack. Configured `app.agents` factories implement Filter, Interview and Report via the existing bounded runtime. Schedule stays unavailable unless separately configured. Missing evidence is unknown; no scoring, ranking or hiring recommendations. Source-diverse overlapping chunks use bounded lexical retrieval instead of an independent embedding HTTP client. Existing document extraction and exact citation validation remain authoritative.

`WorkflowRequest.action` and natural-language `candidate_workflow.action` additionally accept `prepare_interview`, with an explicitly selected applicant and empty data. It calls Interview for a five-question `Guide`, then signed `workflow_prepare_direct {case_id,expected_version,language,questions}`. Approved current criteria and source snapshots are required; direct guide versions are independent of booking drafts. This version sets all follow_up values null.

Public `Case` gains `direct_guide: {version,language,questions}|null` and `direct_interview: SessionSummary|null` identifying that guide's own session even if a booked session is newer. SessionSummary adds `guide_version` (zero for historical bookings). General `interview` still describes the latest session for compatibility. Expired/unavailable historical session answers are omitted from new evidence rather than blocking fresh workflows; the case owner/access checks still apply.

Browser-only, authenticated and CSRF-validated `workflow.interview.create {case_id,guide_version,client_request_id:UUID}` returns `{case,session_id,interview_url}`. It is never a model tool or signed callback. Case locking plus one session per direct guide and one key per case makes retries idempotent. A purpose-separated HMAC using the database secret, database identity, case/version and request UUID rederives the same bearer for an authorized retry; only its hash is persisted. Rotation invalidates retry derivation. Direct sessions use negative reserved draft_version values internally to preserve the existing positive booking-version uniqueness constraint; additive guide_version/client_request_id fields preserve booked records. A different UUID for the same guide is rejected. Existing expired/revoked/stale links cannot be recovered.

No calendar or mail write occurs. The URL is returned only to the authenticated owner; it is excluded from public case summaries, model inputs and activity. Browser localStorage keeps only the nonsecret request UUID, namespaced by database/user/case/guide, enabling authenticated recovery after a lost acknowledgment or reload; a browser without the key prepares a new guide. Candidate submission/expiry/revocation rules above apply unchanged.

The OWL panel is available across Recruitment screens, 420px by default and 360–640px adjustable. It uses an explicit current-record selection chip, never silently switching candidate focus. Native views and chat remain independent; this does not use OdooBot. Source checks run before/after specialist calls and before delivery, while every private streamed delta still checks cancellation/deadline without a per-token Odoo round trip.


## Reviewed full workflow release — 2026-10-31

`orchestrate` accepts the same optional `{schedule: ScheduleInput}` data as `schedule`. It requires browser-approved current criteria and runs the configured Filter, Schedule and Interview adapters through the bounded gateway. Missing scheduling details produce persisted needs-input with the real screening preserved; attendee availability is never invented. A complete result is an unbooked preview and five-question guide, with automation_state `review`. No Report activity is fabricated for this preparation run.

`workflow_automation_start` requires already approved current criteria; it cannot approve them. Automatic scheduling/dispatch callbacks are excluded from signed capabilities. All reservation/mail creation goes through the existing `confirm` browser action and version/hash-bound approval, including full workflows; no internal automatic-confirm bypass remains. Confirmed full-workflow invitations wait for the candidate's explicit accept/decline response. Existing guided and direct sessions keep their behavior. The expiry cron is installed inactive; elapsed time alone does not establish participation or a hiring judgment.

Schedule may be configured with `app.agents:schedule_adapter`; its extraction uses only supplied scheduling information and has no business write tools. Production SMTP/cron remain disabled, so confirmation returns configuration-required with no effects until delivery is deliberately configured. Successful reservation/mail creation is verified separately with disposable local capture.

Native skill declarations remain visible; automated matching scores, matching filters/gauges and matching-talent entry points are hidden by the recruitment UI. These native comparison fields are never evidence tools or model inputs. Demo skill levels are explicitly synthetic self-report.
